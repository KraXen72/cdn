Scenwise DWN edit stage v2 · post-generation overlay
Architecture exploration

One patch layer between generated and published DWN

  • The generator produces an immutable baseline DWN.
  • Reviewers save corrections as patches.
  • The patch engine updates network geometry and the routing graph.
  • Temporary and permanent corrections use the same patch system.
  • After regeneration, keep a patch only if the reviewer would make the same correction again.

    Small operation vocabulary
    
      
    Use a small set of patch operations. Combine them when needed.
    
      
    
        
    ADDAdd overlay-owned network content
    • Missing crossing or path.
    • Creates geometry and corresponding graph connectivity.
    • Can later be removed without touching baseline.
    
        
    REMOVERemove overlay-owned content
    • Inverse of ADD.
    • Useful for retiring a manually-added element.
    • Different from suppressing generated data.
    
        
    SUPPRESSHide baseline content
    • Baseline remains immutable.
    • Used for wrong generated paths, closures, or replaced geometry.
    • May be temporary via expiry.
    
        
    SET_ATTRIBUTESOverride routing / accessibility data
    • access=false, surface, width, tactile paving, etc.
    • Can expire.
    • No geometry rewrite needed.
    
      
    
      
    Reshape / move can be SUPPRESS old geometry + ADD replacement geometry. Add a MOVE operation later if real cases need it.

    What happens after source data or the generator changes?
    
      
    
        
    1 · Generate run N+1fresh immutable baseline
    
        
    2 · Resolve patch targetprefer stable BGT/source refs + local scope
    
        
    3 · Ask: same intent?would reviewer still make the exact same patch?
    
        
    4 · Reapply or reviewsend to review when the correction no longer applies cleanly
    
        
    5 · Build effective DWNgeometry + graph stay consistent
    
      
    
      
    
        
    Baseline still has the same problem
    • Patch changes the same real-world section.
    • Reapply.
    
        
    Generator/source already fixed it
    • Applying patch makes no difference.
    • Satisfied / retire candidate.
    
        
    Target changed materially
    • Old edit would no longer be the same reviewer action.
    • Needs review.
    
        
    Cannot resolve target confidently
    • Do not nearest-neighbour guess.
    • Do not auto-apply.
    
      
    
      
    For the Netherlands, start with BGT/source lineage plus a local geographic scope. Add custom geo-based identity later if real cases show that this is not stable enough.
    
    
    


    
    
      
    Does V2 still cover what V1 was designed for?
    
      
    Yes. V1 replayed corrections across source updates and stopped when the affected area changed too much. V2 keeps that behavior. It compares the local generated DWN state instead of patching normalized source data before generation.

    What changed from V1: the replay semantics survive; only the patch location moved. V1 patched normalized source data before generation. V2 patches the generated DWN baseline after generation.
    

      
    
        
    Example · building overlap
    • Before: generated line cuts through a building footprint.
    • Patch: SUPPRESS the bad section + ADD a short detour around the facade.
    • After regeneration: if the generator now creates the detour itself, status becomes SATISFIED.
    
        
    Example · source geometry shifts 30 cm
    • BGT geometry changes slightly, but reviewer intent is unchanged.
    • If local generated geometry is still equivalent to expected_before within tolerance, reapply.
    • A global stable geo ID is not required for this case.
    
        
    Example · sidewalk is rebuilt
    • Source feature split, crossing moved, geometry materially changed.
    • Old patch would no longer be the exact reviewer action.
    • Mark NEEDS_REVIEW instead of forcing replay.

    Questions before implementation
    
      
    
        
    Target representation
    • Exact generated feature?
    • Source refs + geometry scope?
    • How much semantic context is enough?
    
        
    Patch granularity
    • Operate on centerline segments, crossings, graph edges, or a logical pedestrian-network feature?
    • Which representation is canonical?
    
        
    Materialization strategy
    • Persist effective geometry/graph?
    • Compute overlay at read-time?
    • Likely hybrid: materialize changed rows for fast routing.
    
      
    
      
    These can be decided during implementation. They do not change the basic patch model.
